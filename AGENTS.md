## 24. Required Development Workflow

Default website-development workflow:

1. Work on `develop`.
2. Inspect existing implementation before editing.
3. Make the smallest coherent set of changes.
4. Run appropriate local validation.
5. Inspect `git diff`.
6. Review changes on `dev.optisoftware.com`.
7. Only then promote approved changes toward `main`.

When a request could affect production, prefer making the change on
`develop` and stop after validation unless the user explicitly requests
promotion to `main`.

Never push directly to `main` unless explicitly requested.

## 27. AWS Safety Rules

Never run destructive AWS commands without explicit approval.

Examples include:

- Deleting S3 buckets
- Deleting CloudFront distributions
- Deleting Route 53 records
- Deleting Lambda functions
- Deleting API Gateway APIs
- Deleting SES identities
- Deleting IAM roles
- Deleting CloudFormation stacks
- Deleting VPC resources
- Terminating EC2 instances
- Releasing Elastic IP addresses

Before proposing destructive infrastructure work:

1. Inventory the resource.
2. Identify dependencies.
3. Explain the impact.
4. Prefer reversible changes.
5. Obtain explicit approval.

## 36. Required Agent Behavior Before Editing

Before modifying files:

1. Read this `AGENTS.md`.
2. Confirm the current Git branch.
3. Check `git status`.
4. Inspect the files relevant to the requested change.
5. Identify dependencies.
6. Briefly state what will be changed.
7. Preserve unrelated working functionality.

Do not blindly replace files without inspecting the existing
implementation.


## 37. Required Agent Behavior After Editing

After making changes:

1. Run appropriate syntax or validation checks.
2. Inspect the changed files.
3. Run `git diff --stat`.
4. Review `git diff` for unintended changes.
5. Summarize exactly what changed.
6. Identify anything not tested.
7. Identify anything requiring browser or dev-site verification.
8. Stop before commit or push unless explicitly requested.
